# 实验装置说明与关键决策

实验装置由轨迹生成器、负载台、实验记录表写入通路与拉起脚本组成，复用正式项目的网关作流量入口，被测对象是原生引擎副本。装置与正式项目代码分离，装置目录整体删除后正式项目不受影响（R1）。

## 主链路

负载台读取轨迹文件，按每个请求的到达时刻发出请求，请求携带会话编号与策略字段（D2、D3）。网关透传会话编号与策略字段，按前缀亲和把请求路由到引擎副本；探针判定副本不健康时摘除该副本，在飞请求改路到其余副本重新计算，改路记一条事件进演练记录。引擎副本只带本地前缀缓存。负载台统计每轮的完成请求数与延迟分布。决策服务按在线查表结果写决策记录（D9），装置阶段只定表结构与写入通路；取回组件挂载后，装置组成与运行方式不变。

## 组件职责

### 轨迹生成器

轨迹生成器从 Mooncake 公开的 agent trace 取底稿，清洗剔除缺失长度或到达时刻字段的请求，得到到达间隔与输入长度的原始分布。按格生成轨迹时，轨迹生成器按该格长度档的形状重采样输入长度（D5），按该格压力档缩放到达间隔（D7），按该格比例构造共享前缀（D6）。输入长度以 token 计，轨迹生成器用该档模型的 tokenizer 把文本校准到目标 token 数（R8）。同一格同一 seed 重新生成的轨迹文件与已有文件逐字节一致，seed 记进轨迹元数据（D1）。

真实 trace 的前缀占比达不到该格目标时，轨迹生成器把合成公共前缀拼进请求头部补足差额，合成占比写进轨迹元数据（D4）；缺这项记录时命中率无法归因。截断发生在采样之后：先截断再采样会把长档的分布形状压扁，长度档之间的差异随之失真。

### 负载台

负载台按轨迹回放请求流，每轮统计完成请求数、TTFT 分布与前缀命中率，把每轮统计写进该轮目录的 run_meta.json（D13）。负载台每秒采样引擎等待队列长度与本进程 CPU 占用、连接数，采样值是压力档验证（D7）与饱和判定（D11）的输入。每轮结束负载台按三步判定该轮有效性：对账、饱和、压力档，判定失败的轮移进该轮目录的 quarantine/ 子目录并写明原因。

### 记录通路

四张表的粒度与关联键由 D8 给出，落盘文件名映射由 D13 给出。写入通路分三条：负载台写演练记录与每轮统计；决策服务写决策记录；引擎侧组件写驱逐事件与退回、降级事件。装置阶段只定表结构与写入通路，写入方接入后表结构不变。

## 装置目录与命令入口

装置代码集中在仓库的 bench/ 目录，每个文件只承担一件事：

```
bench/
  run.py        唯一命令入口（D12）
  config.py     参数唯一来源
  tracegen.py   轨迹生成
  loadgen.py    负载台
  record.py     实验记录表写入
  scripts/      环境自检等辅助脚本
  requirements.txt
```

数据与结果不进仓库，落 D13 声明的数据目录，根路径由环境变量 `KVFERRY_BENCH_DATA_ROOT` 指定，缺省 `~/kvferry-bench/data`。

## 参数总表

只列会改变读数的参数，常量集中在 `bench/config.py`。

| 参数                      | 取值                                  | 作用                                                               |
|---------------------------|---------------------------------------|--------------------------------------------------------------------|
| `--tier`                  | S / M / L                             | 模型档，决定引擎副本、tokenizer 与输入上限（D5）                   |
| `--cell`                  | 格 ID（D6 命名），传 all 表示全族串行 | 该轮跑哪个格                                                       |
| `--mode`                  | cold / hot，传 all 表示两种各跑       | 冷热跑法（R4）                                                     |
| `--group`                 | D14 的六个组 ID                       | 对照族的组别                                                       |
| `--kv-pool-gib`           | 全族取同一值                          | KV 池容量，六组对照的前提（R3）                                    |
| `--replicas`              | 全族取同一值                          | 引擎副本数（R3）                                                   |
| `--reps`                  | 缺省 2                                | 每格跑的轮数，复跑判定（D10）需要两轮                              |
| `LOW_LOAD_SCALE`          | 0.5                                   | 低压力档到达率相对基线完成速率的倍数                               |
| `HIGH_LOAD_SCALE`         | 1.5                                   | 高压力档到达率的初始倍数，压力档验证不达标时按作废分支调整后重生成 |
| `MEASURE_WINDOW_S`        | 300                                   | 压力档验证的测量窗口长度（D7 在此窗口内计算）                      |
| `SAT_SAMPLE_INTERVAL_S`   | 1                                     | 队列水位与饱和采样的间隔                                           |
| `KVFERRY_BENCH_DATA_ROOT` | 缺省 `~/kvferry-bench/data`           | 数据目录根路径                                                     |

两个倍数是首轮校准的初始值：0.5 倍使队列基本为空，1.5 倍使队列持续积压；首轮实测偏离 D7 判定条件时调整倍数并重新生成轨迹。基线完成速率的估算是负载台先在 native 组跑一轮中等长度轨迹，取该轮的完成速率。

## 轮次作废分支

两种情况整轮作废：同一轨迹重跑两次的请求数或 token 数不相等，或 P50 TTFT 偏差超过 10%（D10）；负载台的 CPU 占用或连接数先于引擎达到饱和（D11）。作废轮移进该轮目录的 quarantine/ 子目录，作废原因写进该轮 run_meta.json。压力档验证不达标的格按 D7 判定，轨迹生成器调整到达间隔倍数重新生成轨迹，重跑该格。

## 日志

负载台在每轮开始与结束时各记一条，字段含轮次编号、格参数与时刻。请求完成时记 request id、会话编号、完成时刻与 TTFT。负载台每秒采样引擎等待队列长度与本进程 CPU 占用、连接数。请求输入内容不写日志。

## 契约

### D1 轨迹文件
轨迹文件为 JSON Lines：首行是元数据对象，字段含 prefix_ratio、length_tier、load_tier、model_tier、synthetic_ratio、n_requests、seed；其余每行一个请求对象。文件名为 `trace-<格 ID>.jsonl`，落 traces 层，换格换文件，不改代码。

### D2 轨迹请求字段
每个请求记录四个字段：t_ms（相对轮起点的到达时刻，毫秒）、n_input（输入 token 数）、session（会话编号）、text（输入文本）。

### D3 会话编号
负载台按会话生成会话编号，同一会话的请求共用一个编号。网关只透传会话编号，不生成。

### D4 合成前缀
目标前缀比例高于真实占比时，轨迹生成器从通用语料取片段拼接成公共前缀，按差额 token 数补进请求头部。合成段 token 数占输入 token 数的比例写进轨迹元数据的 synthetic_ratio 字段。

### D5 输入长度三档
短档为 512 到 2048 token 的均匀分布；中档为 2048 到 8192 token 的对数均匀分布；长档 90% 的请求落在 12288 到 16384 token、其余 10% 落在 8192 到 12288 token。采样后按模型档输入上限截断：S 档 16K、M 档 30K、L 档 16K。

### D6 共享前缀比例三档
三档取 0%、50%、80%。比例指每格内请求之间可共享前缀占输入 token 数的比例。

### D7 压力档判定条件
高压力档：测量窗口内引擎等待队列长度始终大于 0，且队列非空状态连续保持至少 30 秒。低压力档：队列非空时间占测量窗口的比例低于 10%。

### D8 实验记录表
四张表全部按 request id 或块哈希关联：决策记录每请求一条，退回与降级事件每次一条，驱逐事件每块一条，演练记录每次一条。逐出的保留动作与层级、升温的搬回字节与耗时记进各自的事件表，不进决策记录。

### D9 决策记录字段
字段全集为十一项：会话编号、request id、命中深度、层位、动作（取回、重算、不可取回）、取回与重算的估计耗时、触发时点、置信档、表版本、实际取回完成时刻、TTFT。

### D10 复跑一致性
同一轨迹重跑两次，完成请求数与 token 数精确相等，P50 TTFT 偏差不超过 10%。超出该偏差的轮次作废。

### D11 负载台饱和判定条件
负载台每秒采样本进程 CPU 占用与连接数。负载台先于引擎饱和的轮次作废。

### D12 命令入口
装置入口是 `python3 bench/run.py`，子命令五个：tracegen（生成轨迹）、up（拉起网关与引擎副本）、run（跑一轮或全族）、reset（手动重启副本并清空 KV 池与存储层）、collect（汇总每轮结果）。

### D13 数据目录
数据目录由 `KVFERRY_BENCH_DATA_ROOT` 指定，缺省 `~/kvferry-bench/data`，仓库内只存脚本与清单。traces 层按模型档存轨迹文件；runs 层按模型档、组、格存每轮目录，每轮目录含 run_meta.json 与四张表的落盘文件：decision.jsonl、fallback.jsonl、evict.jsonl、drill.jsonl；判定作废的轮移进同格的 quarantine/ 子目录；summary 层存 collect 产出的 summary.csv。

### D14 决策配置键
决策动作配置键为 fetch-policy，取值 force-fetch、force-recompute、static、online；静态预算配置键为 fetch-budget 与 connector-budget，单位字节。配置由 up 写进各组件启动参数。

### D15 组与存储挂载
native 组不挂存储；fetch-all 与 recompute-all 组挂 KVFerry 存储，recompute-all 组的存储写入照常开启；sticky-static 组挂分层存储；connector 组用 vLLM 自带的 CPU offload；kvferry 组挂 KVFerry 存储。

## 取舍

### R1 装置与正式代码分离
结论：装置目录可整体删除，网关复用正式项目组件，不进装置目录。
原因：装置是临时设施，正式项目的交付物不含装置。

### R2 会话编号由负载台生成
结论：会话编号由负载台按会话生成，网关只透传。
原因：与生产链路的会话语义一致，网关另建生成逻辑会留下技术债。

### R3 KV 池容量与副本数不进族
结论：KV 池容量与副本数全族取同一个值。
原因：六组对照读同一格，容量或副本数不同则对照失去前提。

### R4 冷热是每格的两种跑法
结论：冷热不占族维度，每格冷、热各跑一轮，第一轮全部跑完再考虑砍格。
原因：冷热差异是跑出来的结果，预先砍格会丢掉对照。

### R5 压力档按队列积压定义
结论：压力档按队列非空时长定义（D7）。
原因：到达率的短时突发会把低压力轮误判成高压力，队列非空时长直接反映积压。

### R6 前缀三档取 0%、50%、80%
结论：三档取 0%、50%、80%（D6）。
原因：三档与 Mooncake 公开的实测前缀复用区间对齐，更高的比例要靠合成前缀构造。

### R7 模型档输入上限
结论：S 档与 L 档输入上限 16K，M 档 30K（D5）。
原因：上限取单卡显存扣除权重占用后能同时容纳多条会话的最大长度，L 档 30K 只够一到两条并发。

### R8 轨迹存文本不存 token 序列
结论：轨迹文件存输入文本，引擎收到请求后自行 tokenize；n_input 由轨迹生成器用该档 tokenizer 校准（D2）。
原因：轨迹文件与 tokenizer 实现解耦，换档换 tokenizer 不重造轨迹。

### R9 语料与模型统一走 ModelScope
结论：轨迹底稿语料与模型权重都从 ModelScope 获取。
原因：获取通道统一，机器不依赖其它外部源。
