## 外部事实
- 分层 KV 存储与 RDMA 传输已有产品。Mooncake Transfer Engine 做零拷贝 RDMA、GPUDirect、拓扑感知选网卡，TCP 兜底，在阿里与蚂蚁部署；LMCache 做 HBM/DRAM/NVMe 三层与跨实例共享；NVIDIA Dynamo KVBM 分 G1–G4 四档，传输走 NIXL。参考：[Mooncake 进展](https://www.infoq.cn/article/EhS1Zy1CiUHtJ7mheqmv)、[Dynamo KV offloading](https://docs.nvidia.com/dynamo/v1.5.0/kubernetes/kv-cache-offloading/overview)。

- 加载 KV 不一定比重算快，收益取决于带宽与负载。参考：[LMCache 论文解析](https://gentlecold.top/20260613/lmcache-paper-analysis/)。

- LMCache 团队 2026 年 5 月 MI300X 实测：低负载 8 用户、32K 上下文，原生前缀缓存完成 52 个请求，LMCache 完成 25 个；高负载 32 用户、100K 上下文，TTFT 102.17 s，原生 34.59 s。offload 静态开启后收益随负载档翻面。参考：[MI300X 实测](https://www.51cto.com/article/853886.html)。

- 生产默认路由仍是前缀亲和（sticky）。取不取、从哪层取都由静态配置给出，没有在线组件读当前带宽与计算占用。参考：[vLLM/SGLang KV 调研](http://juejin.cn/entry/7685238126571208731)。

- FAST'26 归纳三个矛盾：数据放不对、复用算不对、调度看不见，KVFerry 接"复用算不对"这个矛盾。参考：[FAST'26 归纳](https://github.com/ForceInjection/forceinjection.github.io/blob/main/09_inference_system/kv_cache/README.md)。

- 上游 vLLM 已带 KV 传输挂载接口和官方 offload 实现。挂载接口提供命中查询、加载、保存三类回调，支持异步加载和按层等待；官方 offload 按 chunk 加载，命中判定只看连续前缀，同步还是异步由静态字节预算决定；上游在取回与重算之间不做在线成本决策。

- KV 形态不止页式块一种。会话级产品把循环状态等形态纳入 KV 管理，与页式块并存；决策层要处理多种形态，不能默认只有页式块。参考：Kimi K3 技术报告与 NVIDIA Dynamo KVBM 的公开讨论。

- 会话级 KV 复用的收益已有外部实测。CommitKV 在 Qwen3-VL-8B、256 token 预算下把峰值显存降低 54%–55%，端到端提升 2.12–2.17 倍；Helios 在 40,960 token 上下文、SGLang 基线上把前缀命中率提高 1.3–3.5 倍，吞吐提高 1.2–1.5 倍，token 成本降低 16%–37%。这两项说明保留与复用有收益，但没有回答请求到达时该取回还是重算。参考：CommitKV（arXiv 2608.07855）、Helios（ICPP Workshops '26，DOI 10.1145/3816891.3834846），外部数据未复现。

## 仍然成立的问题
- 决策只能静态
取回还是重算，现在由静态配置决定。同一份配置换机型或换负载档，收益方向就可能反转。上游 offload 的字节预算同样是静态配置，没有组件在线计算这笔成本。
根因在代价表缺失。带宽与重算成本都没有按机器标定，决策依赖经验值，换机型也没有重标定入口。没有表，在线计算就缺少输入。

- 决策覆盖面不全，缺少形态和时点
形态上，现有取回路径默认 KV 是页式块。遇到会话状态等形态时，要么算错成本，要么直接不可用。决策结果里也没有“不可取回”这一档，强行取回的收益无法平衡。
时点上，现有实现只在请求到达时选一次。逐出时，放哪层、留多久没有决策；同一会话再活跃时，要不要提前取回也没有决策。冷会话与热会话的 KV 受到同样对待，冷 KV 占用近层存储。
一个只覆盖一种形态、只选择一个时点的决策器，上线后也无法应对真实负载。

- 执行器不重叠，决策正确时收益被削弱
取回占用网卡和 PCIe，计算占用 SM。两者串行时，取回耗时全额计入 TTFT。
决策决定是否取回，执行决定取回时能否与计算重叠。决策正确但执行串行，收益会显著降低。

- 降级后语义断档，异构集群数字不可比
非 RDMA 机器上，KV 复用路径整体不可用，或者退到另一套语义，两类机器的数字无法比较。这条决定方案能否在异构集群统一交付，也决定实验报告能否跨机型对照。

## 需求强度
8B GQA 模型在 FP16 精度下每 token 的 KV 是 128 KiB，30K 上下文的前缀占 3.8 GiB。
这 3.8 GiB 走取回还是走重算，取决于传输带宽与重算成本。量级推算（A100 bf16、8B、prefill 按 50% MFU，取回不含固定开销）：

| 路径               | 有效带宽  | 取回 3.8 GiB | 重算 30K token |
|--------------------|-----------|--------------|----------------|
| 跨节点 IB 400 Gbps | 50 GB/s   | 0.08 s       | 3 s            |
| IB 200 Gbps        | 25 GB/s   | 0.15 s       | 3 s            |
| PCIe Gen4 x16      | 20 GB/s   | 0.2 s        | 3 s            |
| 100 GbE TCP        | 12.5 GB/s | 0.30 s       | 3 s            |
| 25 GbE TCP         | 2.8 GB/s  | 1.4 s        | 3 s            |
| 10 GbE TCP         | 1.1 GB/s  | 3.5 s        | 3 s            |

KV 池容量决定复用需求的规模。80 GB 卡的 KV 池约 60 GB，放得下十五个 30K 请求。并发越过这条线，前缀只能放到 DRAM、NVMe 或远端。这时每个命中请求都要走一次取回决策。

## 现勘：vLLM 引擎的语义勘察
| 核实项       | 上游行为                                                                                       |
|--------------|------------------------------------------------------------------------------------------------|
| KV 块信息    | 块分配回调可以获取每个 KV 块的编号与哈希                                                       |
| 命中查询     | 仅返回连续前缀的命中 token 数及是否涉及异步加载，不支持非连续命中                              |
| 异步加载     | 支持远程 KV 等待状态，加载完成后通知调度器，再进入 prefill                                     |
| 按层等待     | 每层 attention 前后提供等待回调，调用点位于计算图捕获断点                                      |
| 图捕获       | 默认优化级别下 prefill 与混批采用分段捕获，挂载方可以声明强制分段                              |
| 块规格       | 默认每块 64 token；8B GQA、FP16 配置下单块约 8 MiB                                             |
| 块哈希       | `hash(父块哈希, 块内 token IDs, 附加键)`，附加键包含 LoRA、缓存盐及多模态哈希                  |
| 上游 Offload | 支持按 chunk 加载，但命中仍按连续前缀计算；同步/异步采用静态字节预算，不进行取回与重算成本比较 |

vLLM已经具备块级信息、远程加载和按层等待能力，但在命中语义与成本决策方面存在限制。
