# 实验装置用户手册

## 环境准备

### 工具与显存

宿主机跑 Linux，装 Python 3.10 以上、NVIDIA 驱动与 ModelScope CLI：

```bash
python3 --version
nvidia-smi --query-gpu=memory.total --format=csv
pip install -U modelscope
```

显存判断标准按模型档：S 档不低于 7 GB，M 档不低于 22 GB，L 档不低于 18 GB，配置低于下限的机器不跑该档。数据目录根路径由 `KVFERRY_BENCH_DATA_ROOT` 指定，缺省 `~/kvferry-bench/data`，数据目录所在的磁盘按 18 格轨迹与全部轮次结果预留空间，建议可用量不低于 20 GiB。

### 模型下载

三个档位的模型都从 ModelScope 下载（R9）：

```bash
modelscope download --model Qwen/Qwen3-1.7B --local_dir ~/models/qwen3-1.7b
modelscope download --model Qwen/Qwen3-4B --local_dir ~/models/qwen3-4b
modelscope download --model Qwen/Qwen3-8B --local_dir ~/models/qwen3-8b
```

判断标准：三个目录里都有该模型的权重文件。

### Python 环境

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r bench/requirements.txt
```

判断标准：激活环境后 `python3 bench/run.py --help` 打印 tracegen、up、run、reset、collect 五个子命令（D12）。bench/requirements.txt 固定 vLLM 0.34.0，与 scripts/requirements.txt 同版本。

## 跑分前检查清单

按顺序过，每条不过先修再往下走：

| 项          | 判断标准                        | 怎么查                                             |
|-------------|---------------------------------|----------------------------------------------------|
| Python 依赖 | run.py 打印五个子命令           | `python3 bench/run.py --help`                      |
| 装置自检    | preflight 无 FAIL 项            | `python3 bench/scripts/preflight.py --tier <档>`   |

| 轨迹齐全    | traces 层该档 18 个轨迹文件     | `ls <数据目录>/traces/<tier>`                      |

## 底稿与语料

轨迹底稿与语料都落数据目录的 source 层（D13），tracegen 经 --base-trace 与 --corpus 读取。

底稿取 Mooncake 官方仓库的 FAST25-release trace，四份 JSONL 各含 timestamp（相对秒）、input_length、output_length 与 hash_ids 字段：

```bash
for f in arxiv-trace/mooncake_trace traces/conversation_trace traces/synthetic_trace traces/toolagent_trace; do
  curl -L -o "<数据目录>/source/$(basename $f).jsonl" \
    "https://raw.githubusercontent.com/kvcache-ai/Mooncake/main/FAST25-release/$f.jsonl"
done
```

装置默认底稿取 toolagent_trace.jsonl（agent 场景，与 4.0 的 agent trace 口径一致）。语料取 NLTK gutenberg 语料包，解包拼接为纯文本，语言与底稿场景一致取英文：

```bash
curl -L -o "<数据目录>/source/gutenberg.zip" \
  "https://raw.githubusercontent.com/nltk/nltk_data/gh-pages/packages/corpora/gutenberg.zip"
python3 - <<'EOF'
import zipfile
root = '<数据目录>/source/'
with zipfile.ZipFile(root + 'gutenberg.zip') as z:
    with open(root + 'corpus-en.txt', 'w', encoding='utf-8') as out:
        for name in sorted(n for n in z.namelist() if n.endswith('.txt')):
            for line in z.open(name).read().decode('utf-8', 'replace').splitlines():
                s = line.strip()
                if s:
                    out.write(s + '\n')
EOF
```

判断标准：source 层有底稿 JSONL 与 corpus-en.txt，corpus-en.txt 为非空纯文本行；抽任一行底稿含 timestamp、input_length、hash_ids 三个字段。官方 trace 无会话字段，会话编号按 D3 按请求序号生成。

## 生成轨迹

```bash
python3 bench/run.py tracegen --tier M --dry-run                # 打印 18 格计划，不落盘
python3 bench/run.py tracegen --tier M \
  --base-trace <底稿 JSONL> --corpus <语料文本> --baseline-rate <req/s>   # 全部 18 格
python3 bench/run.py tracegen --tier M --cell p50-lenmid-high \
  --base-trace <底稿 JSONL> --corpus <语料文本> --baseline-rate <req/s>   # 单格重新生成
```

底稿与语料先落到本地，路径经 `--base-trace` 与 `--corpus` 给出；`--baseline-rate` 用 native 组中等轨迹实测的完成速率。

判断标准：`traces/<tier>/` 下出现 18 个 `trace-<格 ID>.jsonl`（4.2 的 18 格表）；抽查任一文件，首行元数据含 prefix_ratio、length_tier、load_tier、model_tier、synthetic_ratio、n_requests、seed 七个字段（D1）。同一格带同一 seed 重新生成，文件与已有文件逐字节一致；不一致判装置不稳，先修轨迹生成器再开跑。

## 拉起

```bash
python3 bench/run.py up --tier M --kv-pool-gib 8 --replicas 1
```

KV 池容量与副本数全族取同一值（R3），跑族前定好，六组共用。up 先校验网关端点 `KVFERRY_GATEWAY_ENDPOINT` 可达（未配置或不可达时报错退出非 0），然后拉起引擎副本并逐个做健康检查，全部通过命令才返回，退出码 0；网关的拉起由网关自己的启动入口负责（D12）。改过装置代码或换了模型档时重新执行 up，up 会先停掉旧副本再拉起。

up 通过后、开跑前核对两件事：副本注册的模型名与网关健康。

```bash
curl -s http://127.0.0.1:8000/v1/models | grep -o '"id":"[^"]*"' | head -1
curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:9000/health
```

第一条必须返回该档配置口径的模型名（如 S 档 `Qwen/Qwen3-1.7B`）；注册名与负载台请求的模型名不一致时，所有请求会被副本拒绝且轮内无 TTFT（D12）。第二条返回 200。

## 跑格

### 单格

```bash
python3 bench/run.py run --tier M --cell p50-lenmid-high --mode cold --group native
python3 bench/run.py run --tier M --cell p50-lenmid-high --mode hot  --group native
```

`--reps` 缺省 2，两轮结果由负载台自动对账（D10）。

### 全族

`--cell all --mode all` 表示该组 18 格、冷热各 `--reps` 轮串行跑完。负载族原生基线首轮共 72 轮：

```bash
python3 bench/run.py run --tier M --cell all --mode all --group native
```

对照族六组共 432 轮，组间串行：

```bash
for g in native fetch-all recompute-all sticky-static connector kvferry; do
  python3 bench/run.py run --tier M --cell all --mode all --group "$g"
done
```

### 冷热规程

冷态轮由 run 自动执行复位：重启引擎副本，清空 KV 池与存储层，然后跑完整份轨迹。操作者不手动调 reset。热态轮由 run 先按该格的共享前缀比例打一轮预热请求，命中率与 step 时间回到稳态后开始计数，预热轮不计入结果。reset 子命令只供手动干预：跑族中途排查问题时手动复位。

## 收集与汇总

```bash
python3 bench/run.py collect --tier M
```

collect 读 runs 层的全部有效轮，产出 `summary/<tier>/summary.csv`，每行一个格乘一个组乘一个跑法的汇总：有效轮数、TTFT P50 与 P90、前缀命中率、取回字节。判断标准：负载族首轮全跑阶段 72 轮全部有效；作废轮不进汇总，补齐有效轮数后重跑 collect。

## 作废轮处理

判定失败的轮由 run 自动移进该轮目录的 quarantine/ 子目录，原因写进该轮 run_meta.json。手动核查：

```bash
ls <数据目录>/runs/<tier>/<group>/<cell>/quarantine/
cat <数据目录>/runs/<tier>/<group>/<cell>/quarantine/<轮次>/run_meta.json
```

按原因修正（对账超差查负载台稳定性，饱和查负载台所在机器的并发余量）后重跑同一格同一组同一跑法。

## 复现要素

每轮目录的 run_meta.json 记录该轮全部复现要素：模型档、格 ID、跑法、组、KV 池容量、副本数、轨迹文件名与哈希、代价表版本、装置代码版本、机型驱动版本。复现一轮的输入是同数据目录、同 run_meta.json 参数与同轨迹文件。

## 常见故障与处理

### up 健康检查不过

判断标准是 up 退出码非 0。先查显存与模型路径：nvidia-smi 总量是否达到该档下限，模型目录是否有权重文件；再查网关与副本的端口是否被残留进程占用，残留进程处理后重跑 up。

### 轮内全部请求无 TTFT 且秒回

判断标准是 loadgen.log 的 request_done 事件 ttft_ms 全为 null、完成速率远高于基线。根因是副本注册的模型名与负载台请求的模型名不一致，请求被副本以模型不存在拒绝。按「拉起」节的核对命令确认注册名，重跑 up 后重跑该格；半截轮目录删除后重跑。

### 轨迹重生成不一致

判断标准是同一格同一 seed 重新生成的轨迹与已有文件不逐字节一致。查轨迹生成器的语料缓存是否被改动：语料缓存改动会使同一 seed 产出不同文本。处理后删除该格轨迹重新生成，并在该轮 run_meta.json 记录轨迹文件的新哈希。

### collect 有效轮数不足

判断标准是 summary.csv 里某格的有效轮数小于 `--reps`。进该轮目录的 quarantine/ 读 run_meta.json 的作废原因：对账超差查负载台稳定性与同机其它负载，饱和查负载台所在机器的并发余量。修正后重跑同一格同一组同一跑法，再重跑 collect。
